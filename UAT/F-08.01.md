# UAT — F-08.01 Governed Agent Runtime

Status: `UAT_PENDING`.

Story: `S-08.01.01 — Execute agents with explicit tools and approval gates`.

This UAT is separate from engineering CI. It must run against a deployed non-production environment using a real test organisation, real authentication, PostgreSQL and an approved AI provider/model. Do not use production secrets or sensitive customer data.

## Prerequisites

Record:

- tester and date/time;
- environment/base URL;
- commit SHA;
- PostgreSQL version;
- organisation ID;
- test Owner/Admin and Member identities;
- provider/model IDs;
- effective AI rate card/budget state;
- agent definition ID;
- frontend build/commit.

Create an agent with:

- `search.query = read`;
- `work_graph.create_work_item = act_with_approval`;
- a small bounded `max_steps`.

## 1. Default deny

1. Create a second agent without a `search.query` policy.
2. Ask it to find a known test fact.
3. Make the planner propose `search.query`.
4. Confirm the run fails/denies before search execution.
5. Confirm a durable `agent.tool.denied` audit event exists.

Expected: missing policy never behaves like implicit allow.

## 2. Permission-aware read

1. Seed one accessible search document and one restricted document for another user/resource.
2. Run the agent as the Member and ask for the accessible fact.
3. Confirm the agent can use `search.query` and the final response is returned.
4. Confirm the restricted document never appears in tool observations or final response.
5. Revoke the Member's relevant access and repeat.

Expected: the agent cannot read beyond the requesting user's current retrieval boundary.

## 3. No unnecessary content persistence

After the read run, inspect `agent_runs` and `agent_steps` plus the security audit ledger.

Expected:

- objective plaintext is not stored in the agent tables;
- objective SHA-256 and length are present;
- retrieved search content/excerpts are not stored in agent tables/audit;
- final answer plaintext is not stored in agent tables;
- final answer SHA-256 may be stored;
- AI provider credentials are absent;
- bounded IDs/status/digests/timestamps are present.

## 4. High-risk action pauses before mutation

1. Ask the agent to create work item `uat-security-review`.
2. Confirm the run enters `waiting_approval`.
3. Inspect the Work Graph before approval.

Expected: no `manual:work_item:uat-security-review` node exists yet. The pending step contains only the bounded proposed arguments needed for review.

## 5. Reject path

1. Reject the pending action with a reason.
2. Refresh the run.
3. Inspect the Work Graph and step row.

Expected:

- run becomes cancelled/rejected as designed;
- no work item is created;
- pending `arguments_json` and proposal text are cleared;
- durable approval-rejected audit evidence exists.

## 6. Approve path and exactly-once effect

Start a fresh run for `uat-security-review-approved`.

1. Reach `waiting_approval`.
2. Approve it.
3. Confirm approval response itself does not create the work item.
4. Advance the run.
5. Double-click/retry the advance request or issue two near-simultaneous requests from separate clients.
6. Inspect Work Graph and agent steps.

Expected:

- exactly one work item exists for the stable key;
- the step reaches `succeeded` once;
- arguments are cleared after execution;
- `agent.approval.requested`, `agent.approval.approved` and `agent.tool.succeeded` are present;
- concurrent progression is rejected/serialized rather than producing two effects.

Record PostgreSQL behavior explicitly; SQLite unit tests are not proof of the advisory-lock path.

## 7. Permission loss after approval

1. Reach an approved `work_graph.create_work_item` step.
2. Before advancing, remove the Member's underlying write permission/role capability.
3. Advance.

Expected: tool execution fails closed and the work item is not created. Agent policy is not treated as a permission grant.

## 8. Agent disable kill switch

1. Reach `waiting_approval` or `approved` state.
2. As Owner/Admin, disable the agent definition.
3. Attempt approval/advance as the requester.

Expected: no further planner call or mutation occurs until a deliberate new enabled configuration/run is used. If any approved mutation executes after the definition is disabled, the story fails UAT.

## 9. AI provider/model revocation

1. Start a fresh run.
2. Disable/revoke its configured model/provider before planning.
3. Advance.

Expected: planner invocation fails through the governed AI gateway; no tool call executes and no credential is exposed.

## 10. AI hard-budget exhaustion

1. Configure a hard AI budget for the isolated test organisation/user/model.
2. Exhaust the known budget using controlled test calls.
3. Start/advance an agent run.

Expected: planner provider execution is blocked by F-06.02 before credential/provider call, and no tool action occurs.

## 11. Approval expiry and maintenance worker

1. Create a pending approval.
2. In an isolated test setup, make the approval eligible for expiry.
3. Run:

```bash
cd backend
python -m app.agent_worker --once --batch-size 100
```

4. Inspect run/step/audit state.

Expected: approval becomes expired, arguments/proposal text are cleared, action cannot execute and expiry evidence exists.

## 12. Stale state recovery

In a controlled database fixture/staging drill:

- create stale `planning` state older than the recovery threshold;
- create a stale `executing` step for the built-in replay-safe work-item tool;
- run maintenance.

Expected: stale planning returns to a recoverable state; replay-safe action may be requeued; a non-replay-safe tool, if added in future, must fail closed instead of being blindly retried.

## 13. Cross-user and cross-tenant isolation

1. Start a run as Member A.
2. Attempt read/advance/approve/cancel as Member B in the same organisation.
3. Attempt the same from a user in another organisation.

Expected: another user cannot take over the run, and cross-tenant access exposes no run/step fields.

## 14. Frontend/manual workflow

Using the real staging frontend:

1. list enabled agents;
2. create/start a run;
3. observe planning/loading state;
4. observe a read-only completion;
5. observe `waiting approval` with exact proposed mutation arguments;
6. reject once and confirm UI terminal state;
7. approve once and confirm the action does not happen until controlled continuation;
8. continue and confirm success state;
9. trigger denied/expired/budget/provider error states;
10. confirm the UI never displays a mutation as completed before backend evidence says it succeeded.

Capture screenshots where useful, but do not include credentials or sensitive source content in repository artifacts.
