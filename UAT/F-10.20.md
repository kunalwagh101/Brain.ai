# UAT — F-10.20 Direct-Message Lifecycle

Story: `S-10.20.01`

Status: `UAT_PENDING`

Use official WorkOS authentication and PostgreSQL with Alice and Bob as DM participants plus an Owner/Admin who is not a participant.

## Author edit + concurrency

1. Alice sends Bob a private message.
2. Alice edits it from the DM UI.
3. Confirm the current body updates, an **edited** marker appears and the request carries the current expected revision.
4. From a stale client/request, submit another edit with the old revision.

Expected: first edit succeeds and increments revision once. The stale edit returns 409 and cannot overwrite the accepted body. A private `DirectMessageRevision` snapshot contains the prior body/hash only inside the DM persistence boundary.

## Authority boundary

Try PATCH/DELETE as Bob, the nonparticipant Owner/Admin, a revoked Alice, and a reactivated Alice targeting a message from her earlier hidden visibility epoch.

Expected: every unauthorised attempt fails closed (404/403 as applicable). Organisation role alone never provides a content override and old hidden history cannot be mutated after reactivation.

## Retraction + unread

1. Alice sends a message while Bob is away and confirm it becomes Bob's first unread.
2. Alice retracts the message before Bob reads it.
3. Bob opens the DM and the exact message route.

Expected: unread count/first-unread no longer includes the retracted message. Bob receives a body/hash-free tombstone stating the author retracted it. The message has no edit/retract affordance.

## Private-data isolation

Before and after edit/retract, inspect RawEvent, CanonicalEvent, SearchDocument/Ask Brain source state, Work Graph and organisation-wide SecurityAuditEvent records.

Expected: normal DM lifecycle creates none of those company-intelligence/audit records. Only the private current DM row + private revision row change.

## Retention / legal hold

Set `private_message_days` and age a revisioned message beyond the cutoff. Run retention without legal hold, then repeat with legal hold.

Expected: without hold, the private message is deleted and revision rows cascade with it. With hold, neither current nor revision plaintext is purged. No separate derived-content retention policy is used for DMs.

## Browser/security/accessibility

Confirm PATCH/DELETE use same-origin WorkOS routes, bounded JSON and no reusable bearer token in browser storage/code. Keyboard users can reach Edit/Retract/Cancel/confirmation controls and visible focus is present.
