# F-10.10 Live Workspace Updates UAT

Story: `S-10.10.01`

Status: implementation in progress. No DONE/PASS claim until executable frontend/verifier and authenticated WorkOS multi-user browser evidence exists.

## Product acceptance

1. Open the same authorised organisation as User A and User B in separate authenticated browsers.
2. User B posts a root message in a channel User A can read. User A sees the updated channel/unread state without manual reload within 5 seconds while the tab is visible.
3. User B posts a thread reply. The channel root reply count updates automatically; if User A has that thread open, replies re-fetch without exposing a bearer token.
4. User B changes a reaction on a visible selected-channel message. User A's selected channel refreshes automatically.
5. User B sends a participant-authorised DM to User A. User A's DM/Activity state updates automatically.
6. A new mention or thread reply changes Activity/unread without manual refresh.
7. Repeated live checks against unchanged source state do not repeatedly call `router.refresh()`.
8. Hidden-tab checks slow materially versus visible-tab checks; returning to the tab triggers a prompt safe re-check.
9. Going offline does not produce a tight request loop; reconnecting recovers automatically.
10. A transient 5xx/network error backs off and later recovers without user reload.
11. Revoking User A from a restricted channel removes that channel/content on the next changed revision rather than keeping stale content.
12. Revoking DM participant access removes the inaccessible DM state on the next changed revision.
13. Removing organisation membership makes the live BFF fail closed; no stale/cross-tenant content is returned.

## Security/privacy inspection

- Browser live code contains no `Authorization`, `Bearer`, access-token, `localStorage`, `sessionStorage` or IndexedDB credential handling.
- Live-state JSON contains only an opaque revision and safe count/status fields. It contains no channel/DM message body, source excerpt, secret reference, provider credential, API key, agent tool arguments/results or hidden resource name.
- The WorkOS route uses `withAuth()` and revalidates Brain organisation membership server-side.
- Optional channel/DM identifiers are UUID validated before upstream reads.
