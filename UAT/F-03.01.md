## Real-data backend validation

1. Apply migration `20260906_0005` to the test/staging PostgreSQL database.
2. Ingest several real signed Slack deliveries from an authorised test channel.
3. For each accepted event, compare the captured request body bytes with `raw_events.raw_payload`; they must be identical for webhook deliveries.
4. Independently calculate SHA-256 for a captured body and compare it with `payload_sha256`.
5. Verify organisation ID, integration connection ID, provider, source event ID/type, source timestamp, delivery kind and received timestamp.
6. Verify public-channel events have `public_channel` visibility.
7. Verify private-channel events have `private_channel` visibility plus the expected source membership ACL snapshot.
8. Replay identical source event IDs and confirm the unique row count does not increase.
9. Send an oversized payload and verify it is rejected before storage.
10. Revoke/disable the originating integration and confirm new connector deliveries are not persisted.
11. Run a Slack historical backfill and confirm deterministic historical IDs prevent duplication on replay.
12. Confirm new records remain in the initial processing state ready for S-03.02 canonicalisation; no canonical claims are fabricated in this story.
