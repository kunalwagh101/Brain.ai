# F-10.13 Governed Channel Attachments UAT

Story: `S-10.13.01`

Status: implementation in progress. No DONE/PASS claim until executable gates and authenticated browser evidence exist.

## Product acceptance

1. In an organisation channel, upload a supported <=10 MB document from the composer, send it with a caption, and confirm the message shows safe filename/title/type/size/status metadata.
2. Send a supported file with no text and confirm the file-only message is accepted; empty text with no attachments is rejected.
3. Search a unique string from the uploaded file and confirm the authorised result resolves through the existing evidence provenance.
4. In a restricted channel, upload a unique file. A current channel member can read the evidence metadata and find its Search result; a same-organisation non-member cannot.
5. Add a restricted-channel member after upload and confirm Evidence/Search access becomes available without reupload.
6. Remove that member and confirm Evidence, Search and Work Graph access disappear, including historical attachment evidence nodes.
7. Attempt to link another tenant's source, another restricted channel's source, a deleted source and more than five source IDs; all fail closed.
8. Retry the same message with duplicate attachment IDs and confirm only one relation per source/message exists.
9. Retract the message and confirm the conversation exposes no attachment cards while the governed evidence remains available according to its own source lifecycle.
10. Delete the EvidenceSource separately and confirm any unretracted message card becomes safely unavailable/deleted without exposing removed bytes or extracted text.
11. Simulate upload success followed by an ambiguous message-send/network failure. Confirm the UI keeps the uploaded source IDs and reuses the same message idempotency key on retry; changing the text or attachment set generates a fresh key and no duplicate evidence upload occurs.
12. Confirm browser upload/send routes are same-origin, bounded and expose no reusable bearer token.
13. Attempt migration downgrade after creating an attachment-only message and confirm it refuses safely with an operator action message rather than violating the old non-empty-body constraint; after exporting/migrating zero-body rows, downgrade may proceed without deleting EvidenceSource content.

## Required executable evidence

- focused backend attachment/tenant/channel/revocation/deletion tests;
- Alembic single-head + PostgreSQL upgrade/downgrade/re-upgrade;
- `npm run lint` and `npm run build`;
- `node --test tests/channel-attachments-contract.test.mjs` and full frontend source contracts;
- `python scripts/verify_board.py`;
- official WorkOS authenticated multi-user desktop/mobile/keyboard UAT.

Until every required gate passes, keep `S-10.13.01` out of DONE/PASSED.
