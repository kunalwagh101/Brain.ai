# UAT — F-10.05 Governed Files & Evidence Workspace

Status: **IMPLEMENTATION_STAGED / EXECUTION_PENDING**

Story: **S-10.05.01 — Upload, browse and inspect governed documents/transcripts from the workspace**

This UAT is not satisfied by component rendering or API unit tests alone. The accepted product path must use a real authenticated WorkOS browser session, the same-origin Brain BFF, the FastAPI evidence lifecycle, permission-aware Search and Ask Brain.

## Preconditions

- S-02.04 generic evidence ingestion is deployed with its database migration.
- S-05.01 permission-aware retrieval has executable passing evidence.
- S-10.04 official WorkOS/AuthKit production path is activated from genuine npm packages and an integrity-pinned lockfile.
- The frontend and FastAPI point at the same staging environment and Brain organisation data.
- Test users exist for Owner/Admin, Member/Manager, Guest or Executive read-only role, a second Member without restricted access, and a different organisation.
- At least one governed AI runtime is available if the Ask Brain evidence-use step is executed.

## Representative files

Use only synthetic/non-sensitive staging data. Include:

1. UTF-8 `.txt` or `.md` document with a unique searchable fact.
2. `.vtt` or `.srt` transcript with an explicit `Decision:` or `Blocker:` marker.
3. text-extractable PDF.
4. DOCX with paragraph and table text.
5. unsupported binary file.
6. file larger than 10 MB.
7. encrypted or non-text PDF when practical.

Do not use production customer documents for this acceptance run.

## 1. Permission-aware workspace listing

1. Sign in as a user with organisation/resource read permission.
2. Open **Files & evidence**.
3. Verify the list is populated from the authenticated organisation rather than sample data.
4. Verify title, filename, kind, visibility, status, byte size, chunk count, extracted-character count, timestamps and SHA-256/source identifiers reconcile with the FastAPI source record.
5. Verify filtering the browser list does not change backend permissions or reveal hidden source names/counts.
6. Create enough newer restricted records for another user that they would occupy the requested page before permission filtering; verify an older source visible to the current user is still returned.

Pass: SQL/page limiting cannot make authorised evidence disappear merely because newer hidden evidence exists.

## 2. Organisation-visible upload

As Owner/Admin/Manager/Member:

1. Select a supported file under 10 MB.
2. Choose document/transcript, organisation visibility and optional occurred-at timestamp.
3. Upload through the browser.
4. Confirm the browser request targets only the same-origin `/api/brain/.../evidence/uploads` route.
5. Confirm the response is represented after server refresh with `active` state, correct source hash and non-zero chunk/extracted-text values.
6. Reconcile the evidence source, RawEvent, CanonicalEvent, Work Graph evidence node and SearchDocument records.
7. Search for the unique fact and confirm it is returned with matching provenance.
8. Ask Brain about the unique fact and confirm any factual answer cites the uploaded authorised evidence.

Pass: one governed source flows from upload through the existing evidence/search/RAG chain without browser access to the backend bearer token.

## 3. Restricted upload isolation

1. Member A uploads a source with `restricted` visibility.
2. Member A sees the source and can retrieve its unique text through Search/Ask Brain.
3. Member B in the same organisation cannot see the source in the evidence workspace, Search, Project evidence surfaces or Ask Brain citations.
4. A user from Org B cannot read the source by guessing Org A/source IDs; response must be 404/403 with no Org A source fields.

Pass: restricted metadata, counts, titles, hashes and text do not leak.

## 4. Role capability presentation

1. Verify Owner/Admin and the original writable uploader receive `can_delete=true` for an active source according to backend policy.
2. Verify another Member who can read an organisation-visible source receives `can_delete=false` unless they are the uploader.
3. Verify a read-only Executive/Guest does not receive live upload/delete controls.
4. Manipulate the browser DOM/request to attempt a forbidden mutation anyway.

Pass: the BFF and FastAPI reject the mutation; UI capability presentation is never treated as authorisation.

## 5. Idempotency and duplicate submission

1. Capture one browser upload attempt's `Idempotency-Key`.
2. Replay the exact multipart request with the same key and content.
3. Verify the same active evidence source is returned and no duplicate canonical/search projection appears.
4. Reuse that key with different content.

Pass: same-content retry is idempotent; conflicting key reuse fails with 409.

## 6. Format and size failure states

1. Attempt unsupported binary upload.
2. Attempt >10 MB upload.
3. Attempt encrypted/non-text PDF when practical.
4. Verify errors are understandable but do not reflect backend stack traces, provider secrets, WorkOS tokens or raw internal error bodies.

Pass: browser and BFF limits fail closed; no unsupported/OCR behavior is silently invented.

## 7. Governed deletion

As an authorised deleter:

1. Select **Delete source** and verify the UI requires the explicit second confirmation.
2. Delete the source.
3. Confirm returned metadata is `deleted`, `can_delete=false` and has a deleted timestamp.
4. Confirm original `raw_content` is physically cleared according to S-02.04/data-governance behavior.
5. Confirm SearchDocument and CanonicalEvent derivatives covered by the deletion scope are removed/unavailable.
6. Search for the former unique text; no result may remain.
7. Ask Brain the same question; the deleted source must not appear in evidence/citations.
8. Refresh Files & evidence; if deleted metadata remains for lifecycle/audit visibility, it must be clearly labelled deleted and must not expose original content.

Pass: no stale retrievable content survives deletion.

## 8. Integration revocation

1. Upload active generic evidence.
2. Revoke/disable the managed evidence integration through the supported backend/admin path.
3. Verify Search/Ask Brain no longer use the source.
4. Verify the workspace does not present stale content as retrievable/active intelligence.

Pass: revocation is reflected by the next authorised backend read according to S-02.04/S-05.01 contracts.

## 9. Browser security inspection

Inspect HTML, browser JavaScript configuration, Network, Storage and URLs.

Pass only if none contains:

- WorkOS access or refresh token;
- AuthKit encrypted session internals;
- Brain backend bearer token;
- WorkOS API key;
- AWS credentials/secret references;
- OpenAI/provider API keys;
- raw backend stack traces.

The browser may see normal evidence metadata that the authenticated user is authorised to read.

## 10. Accessibility/responsive behavior

Verify keyboard-only operation for:

- Files & evidence navigation;
- filter input;
- upload fields;
- submit button and status feedback;
- provenance disclosure;
- delete first click, explicit confirmation and cancel.

Verify visible focus, status announcements, responsive layout and no horizontal trap on supported mobile/tablet widths.
