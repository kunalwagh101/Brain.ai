# F-09.01 Observability and SLOs — UAT

Status: `UAT_PENDING`

Do not mark this feature ACCEPTED from unit tests alone. Execute this against the actual deployed backend plus the real browser/frontend workflow and the selected monitoring/trace backend.

## Record before starting

- environment / deployment SHA
- tester and date
- PostgreSQL environment used
- Prometheus-compatible scraper/version
- OTLP collector/backend and endpoint class (do not record credentials)
- real Slack/GitHub integration IDs used
- governed AI provider/model used
- representative load/query data set

Do not paste API keys, OAuth tokens, prompts, webhook bodies or customer message/document content into this file.

## 1. Metrics endpoint access

1. Deploy with metrics enabled and a secret `BRAIN_METRICS_BEARER_TOKEN`.
2. Call `/metrics` without the bearer token.
3. Confirm 401.
4. Call with the configured monitoring credential.
5. Confirm Prometheus text is returned.
6. Inspect labels and confirm organisation IDs, user IDs, raw resource UUID paths and customer content are absent.

Expected: monitoring can scrape aggregate telemetry without exposing tenant/cardinality-sensitive dimensions.

## 2. Request correlation

1. Make a normal authenticated API request with `X-Request-ID: uat-request-001`.
2. Confirm the response returns the same request ID.
3. Find the JSON log entry and exported trace using that ID.
4. Confirm method, route template, status, duration, trace ID and authorised organisation context are present.
5. Repeat with an unsafe/high-cardinality supplied request ID such as a path-like value.
6. Confirm Brain replaces it with a generated UUID.

Expected: one bounded request ID correlates response -> logs -> trace without raw URL identifiers becoming metric labels.

## 3. Secret/content redaction

Use synthetic fake values only.

1. In a non-production validation environment, produce a controlled log message containing fake `api_key=...`, `Authorization: Bearer ...`, `access_token=...` and `sk-...` patterns.
2. Confirm the emitted JSON contains `[REDACTED]` and none of the fake credential values.
3. Execute a real AI request and connector event.
4. Search logs/traces for the real prompt/message body and credential value using secure operator tooling.

Expected: real prompt/completion/webhook payload/credentials do not appear in telemetry.

## 4. Liveness vs PostgreSQL readiness

1. With PostgreSQL healthy, confirm `/health/live` = 200 and `/health/ready` = 200 with database `up` plus latency.
2. In a disposable environment, make PostgreSQL temporarily unreachable without stopping the Brain process.
3. Confirm `/health/live` remains 200.
4. Confirm `/health/ready` becomes 503 and database status becomes `down`.
5. Confirm `brain_dependency_ready{dependency="database"}` moves to 0.
6. Restore PostgreSQL and confirm readiness/metric recovery.

Expected: process liveness and dependency readiness are operationally distinct.

## 5. Real connector correlation

1. Trigger one authorised Slack or GitHub webhook/backfill/sync with realistic data.
2. Record the Brain request ID/trace ID.
3. Confirm raw connector telemetry contains provider, integration ID, source event type and created/duplicate state.
4. Confirm sync success/failure telemetry contains provider + integration and a bounded error code on failure.
5. Replay the same idempotent source event.
6. Confirm duplicate telemetry increments while no duplicate canonical evidence is created.
7. Confirm raw message/code payload content is absent from logs/metrics/traces.

Expected: connector incidents are diagnosable without copying source content into monitoring systems.

## 6. Real governed AI correlation

1. Configure one approved real provider/model through F-06.01.
2. Configure a valid rate card through F-06.02.
3. Invoke the model through the governed gateway.
4. Find the child `ai.provider.invoke` trace/span.
5. Confirm organisation, provider, model, latency and internal AI request ID are present.
6. Confirm exact cost metadata appears only when cost resolution is `calculated`.
7. Force one safe provider failure (for example a disposable invalid credential or controlled provider error).
8. Confirm bounded failure status/error telemetry and no upstream response body/credential leakage.

Expected: provider/model latency/error/cost can be diagnosed from the governed path.

## 7. Alert-rule validation

Load `ops/prometheus/brain-alerts.yml` into the target Prometheus-compatible rule engine or validate with `promtool check rules`.

Exercise safely in a disposable/staging environment:

- database readiness down
- controlled connector sync failure
- controlled AI provider failure

Confirm the expected alert enters pending/firing state and its runbook reference is usable.

Do not manufacture production incidents merely to fire an alert.

## 8. SLO measurement

Run representative traffic and record:

- core API request count / 5xx rate
- core API p50/p95 excluding search/AI provider execution
- search p50/p95
- governed AI provider p50/p95 by provider/model
- connector sync failures
- database readiness latency

Initial targets:

- core accepted API availability >=99.9% monthly target
- core structured API p95 <500 ms
- search p95 <1.5 s
- governed AI/provider p95 target <10 s

A short UAT load run validates measurement mechanics only; it does not prove monthly SLO compliance.

## 9. Frontend/manual workflow

1. Open the actual Brain frontend.
2. Execute at least one normal authenticated workflow, one search and one governed AI action when the UI supports them.
3. Use browser network tools to capture the returned `X-Request-ID` without exposing auth headers in this file.
4. Correlate that ID in backend telemetry.
5. Confirm adding telemetry has not broken CORS, loading/error/success states or API response behavior.

If a relevant UI surface is not yet wired, record that fact as `PENDING`; do not substitute sample/mock frontend state.
