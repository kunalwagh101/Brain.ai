# UAT — F-09.03 Deployment, rollback, backup and restore

Status: `UAT_PENDING`.

Story: `S-09.03.01 — Deploy safely with verified rollback and restore`.

This UAT is separate from engineering CI. It must be performed against the selected non-production/staging runtime and a disposable or approved production-like database environment. Never use an uncontrolled copy of sensitive customer production data.

## Prerequisites

Record:

- tester/operator;
- date/time;
- commit SHA;
- Release Gate run URL/result;
- immutable image digest;
- selected runtime/registry;
- PostgreSQL service/version;
- current Alembic revision;
- backup/PITR configuration;
- previous deployed image digest;
- maintenance/deployment window.

OQ-007 must be resolved enough to identify the runtime, registry and managed PostgreSQL used by this exercise.

## 1. Merge/release gate enforcement

1. Create a harmless test PR that intentionally fails one Release Gate command.
2. Confirm GitHub technically prevents merge to the release path.
3. Remove the deliberate failure.
4. Confirm Release Gate passes and the check is required rather than advisory.
5. Record the required-check/ruleset/branch-protection configuration.

Expected: failing Release Gate cannot be bypassed by a normal contributor merge path.

Current repository note: this cannot be accepted merely from the workflow file. The GitHub API reported rulesets unavailable for this private repository on the current plan when Increment 15 was staged.

## 2. Release manifest and immutable image

1. Run Release Gate for the exact candidate commit.
2. Download only the release manifest artifact.
3. Confirm its commit SHA matches the candidate.
4. Publish/promote the OCI image to the selected registry.
5. Resolve and record the registry digest (`...@sha256:...`).
6. Confirm deployment configuration references the immutable digest, not `latest` or another mutable tag.

Expected: one exact commit/image/migration identity can be reconstructed later.

## 3. Pre-deploy database safety

1. Record current Alembic revision.
2. Confirm managed backup/PITR is healthy and record latest recovery point.
3. Where the change/runbook requires it, create a logical backup with `scripts/postgres-backup.sh` in an approved secure location.
4. Verify the `.sha256` sidecar and `pg_restore --list` validation.
5. Confirm the backup archive is not uploaded to source control or an uncontrolled CI artifact store.

Expected: a verified recovery point exists before migration/deploy.

## 4. Migration and forward recovery

In a staging/disposable copy:

1. run `alembic upgrade head`;
2. run `alembic check`;
3. verify core table counts/constraints expected for the release;
4. exercise the documented downgrade only on disposable data;
5. run `alembic upgrade head` again;
6. run `alembic check` again;
7. verify application data used by the drill is still valid where the migration is intended to be reversible.

Expected: migration mechanics work. If downgrade is destructive by design, record that production rollback must use forward recovery/application rollback or restore instead.

## 5. Deployment health gate

1. Deploy the new immutable image using the selected runtime's rolling/canary mechanism.
2. Confirm the new task/container starts with production safety settings.
3. Confirm `/health/live` succeeds.
4. Confirm `/health/ready` remains unhealthy while PostgreSQL is deliberately unreachable, then becomes healthy after PostgreSQL connectivity is restored.
5. Confirm traffic is not promoted to an unready instance.
6. Run authenticated smoke checks for organisation read and one safe core workflow.
7. Inspect structured logs/metrics/traces for the release window without secrets.

Expected: unhealthy instances do not receive normal promoted traffic and the release becomes diagnosable through F-09.01 telemetry.

## 6. Application rollback drill

1. Record the newly deployed image digest and the previous known-good digest.
2. Introduce or use a controlled staging-only application failure that does not corrupt data.
3. Stop/abort rollout.
4. Redeploy the previous immutable image digest.
5. Confirm readiness and authenticated smoke checks recover.
6. Record start/end timestamps and observed application rollback time.
7. Confirm database schema remains compatible with the previous image. If it does not, the release design fails and must be corrected before production use.

Expected: previous image can be restored without ad-hoc source changes or secret changes.

## 7. Backup restore drill

Use a disposable isolated database target.

1. Seed identifiable non-sensitive test records.
2. Create a custom-format backup using `scripts/postgres-backup.sh`.
3. Record archive SHA-256.
4. Mutate/delete the seeded records after backup.
5. Attempt restore without `BRAIN_RESTORE_CONFIRM`; confirm it refuses.
6. Restore with the explicit confirmation token using `scripts/postgres-restore.sh`.
7. Verify the original seeded records are recovered.
8. Run `alembic current` and compare to expected revision.
9. Start the candidate API against the restored database and confirm `/health/ready`.
10. Run representative authorised Slack/GitHub/search/governance reads appropriate to the data set.
11. Record restore start/end timestamps and any manual intervention.

Expected: restored data and application integrity are proven, not merely `pg_restore` exit status.

## 8. Recovery objectives

Record observed values rather than inventing targets:

- release deployment duration;
- application rollback duration;
- logical backup duration/size;
- restore duration;
- latest recoverable point / observed data-loss window from the managed backup mechanism;
- failures/manual steps found.

Product/operations must then agree explicit RTO/RPO targets. Until those targets and a matching exercise exist, Brain must not make unsupported disaster-recovery claims.

## 9. Frontend/manual workflow

From the actual staging frontend:

1. sign in as a real test user;
2. perform one normal read before deployment;
3. deploy the candidate;
4. refresh/re-authenticate if appropriate;
5. repeat the same workflow;
6. confirm no visible schema/API incompatibility;
7. perform the same workflow after the rollback drill;
8. record loading/error/success behavior and screenshots where useful.

Expected: deploy and rollback do not leave the real UI unusable.
