# F-10.06.02 Participant-Safe Direct Messages UAT

Story: `S-10.06.02`

Status: implementation in progress. No PASS/DONE claim is valid until backend execution, PostgreSQL migration checks, official WorkOS activation and authenticated browser UAT all pass.

## Product/privacy contract

Brain-native DMs are private participant-scoped collaboration, not organisation-wide company evidence.

- Production MVP supports one-to-one DMs between two current active same-organisation members whose role allows Brain messaging.
- Only the two participants can list/read the conversation or messages.
- Owner/Admin/Executive roles have no content override merely because of role.
- DM content is not projected to RawEvent, CanonicalEvent, Work Graph evidence, SearchDocument, Ask Brain, Decision Memory, Project Command Centre or Executive Overview.
- Normal DM creation/sending does not create organisation-wide per-message/per-conversation audit records. Aggregate retention-run accounting may record only the number of private messages purged.
- Slack DM ingestion remains separately excluded by OQ-002. Brain-native DM policy is OQ-008.
- Group DMs, external users and participant-scoped AI over DMs are outside this first slice.

## Backend acceptance

1. Member A creates a DM to exact email for Member B; the response identifies B as the other participant.
2. Member B creates a DM to Member A and receives the same conversation ID; duplicate reverse conversations cannot exist.
3. Self-DM creation is rejected.
4. A target outside the organisation is indistinguishable from an unavailable target.
5. A Guest/read-only target cannot be added to a writable DM.
6. Participant A and B can list/read the conversation while both retain Brain native-messaging capability.
7. If an existing participant is downgraded to a role without `native_chat.write`, DM list/read/send all fail server-side even though historical rows still exist.
8. Nonparticipant Owner, Admin and Executive cannot read guessed conversation IDs; return 404/no content.
9. Nonparticipant conversation listing does not expose DM names/participants.
10. DM list/read/create/send require `native_chat.write`; participant membership alone is not enough after a role downgrade.
11. Idempotency-Key replay within the same visibility epoch returns the same message without duplicate storage.
12. Reusing an idempotency key that belongs to an earlier revoked visibility epoch fails with 409 rather than revealing/replaying the earlier message.
13. Message length is bounded at 20,000 characters.
14. Every conversation assigns a monotonic integer `sequence`; each message has one unique `(conversation_id, sequence)` and `next_message_sequence` advances transactionally.
15. Latest bounded history is returned in increasing sequence order.
16. Database composite FK prevents cross-tenant conversation/message attachment.
17. Sending DM messages does not increase RawEvent, CanonicalEvent or SearchDocument counts.
18. DM creation/sending does not create organisation-wide audit rows containing participant pairs, message bodies or per-message hashes.
19. Membership removal or downgrade revokes only that participant's DM side; the other participant can retain permitted historical history but cannot send while the counterpart is unavailable.
20. Re-adding/re-promoting the same user does not silently restore their old DM history. An explicit DM re-initiation is required, and the reactivated participant starts at the then-current `next_message_sequence`.
21. Migration `20260916_0022` creates the participant-scoped DM tables.
22. Migration `20260916_0023` adds explicit private-message retention fields without changing existing raw/derived/audit retention semantics.
23. Migration `20260916_0024` backfills deterministic per-conversation message sequences, adds participant revocation/visibility-epoch fields and preserves existing history for currently active participants.

## Private-message retention acceptance

`private_message_days` is independent of `raw_event_days`, `derived_content_days` and `audit_event_days`.

1. With `private_message_days = NULL`, run retention against an old DM and confirm no DM is deleted.
2. Set `private_message_days = 30` and `legal_hold = true`; run retention and confirm the old DM remains.
3. Set `legal_hold = false` while keeping `private_message_days = 30`; run retention and confirm only messages older than 30 days are deleted.
4. Confirm the `RetentionRun` snapshot records `private_message_days` and exact `private_messages_deleted` count.
5. If at least one recent message remains, confirm the conversation row remains and the same two participants can continue the conversation. If all messages have aged out and the conversation itself is older than the retention cutoff, confirm the empty old conversation metadata is removed as data minimisation.
6. Confirm retention never resets or reuses a surviving conversation's `next_message_sequence`; sequence identifiers remain monotonic even when old messages are purged.
7. Confirm the retention completion audit may include aggregate `private_messages_deleted` only and does not include DM body, participant pair, target email or per-message hash.
8. Confirm `0024 -> 0023 -> 0022` downgrade and forward re-upgrade complete cleanly on PostgreSQL with expected columns/constraints at each revision.

## Frontend/BFF acceptance

1. Direct messages appears as its own Slack-style workspace navigation group.
2. A DM is selected only by a `dmId` found in the server-returned participant conversation list.
3. Guessed/unavailable `dmId` renders no private message content.
4. When `dmId` is active, the server does not also load a default native channel as ambient primary context.
5. New DM uses exact member email and a same-origin WorkOS BFF route.
6. Send uses same-origin WorkOS BFF plus bounded JSON and an Idempotency-Key.
7. Browser code never receives or constructs a reusable WorkOS/FastAPI bearer token.
8. Both mutation routes reject cross-site/cross-origin requests.
9. DM panel visibly states that content is participant-only and excluded from organisation-wide intelligence.
10. If the other participant is revoked/unavailable, historical content remains readable only where authorised and the UI becomes history-only with no active composer.
11. Desktop and narrow/mobile layouts remain usable with keyboard-visible controls.
12. Session expiry, membership removal and role downgrade to a non-messaging role prevent subsequent DM access without requiring client-side revocation logic.

## Explicit negative tests

- Owner who is not a participant cannot open Member A/B DM.
- Admin who is not a participant cannot open Member A/B DM.
- Executive who is not a participant cannot open Member A/B DM.
- Guest/read-only user cannot list/read/send an old DM after role downgrade.
- Membership removal followed by re-add does not automatically restore old DM history.
- Old-epoch Idempotency-Key reuse returns conflict instead of an earlier private message.
- Cross-tenant user cannot create/read/send into the DM.
- Browser cannot submit arbitrary participant IDs; creation accepts only exact target email and server resolves the current organisation member.
- DM service must not import or call RawEvent/CanonicalEvent/SearchDocument projection functions.
- Ask Brain/Search queries must not return a unique phrase that exists only in a DM.
- `derived_content_days` must not implicitly purge DMs; only explicit `private_message_days` may do so.
