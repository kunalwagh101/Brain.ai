# F-10.06.02 Participant-Safe Direct Messages UAT

Story: `S-10.06.02`

Status: implementation in progress. No PASS/DONE claim is valid until backend execution, PostgreSQL migration checks, official WorkOS activation and authenticated browser UAT all pass.

## Product/privacy contract

Brain-native DMs are private participant-scoped collaboration, not organisation-wide company evidence.

- Production MVP supports one-to-one DMs between two current active same-organisation members whose role allows Brain messaging.
- Only the two participants can list/read the conversation or messages.
- Owner/Admin/Executive roles have no content override merely because of role.
- DM content is not projected to RawEvent, CanonicalEvent, Work Graph evidence, SearchDocument, Ask Brain, Decision Memory, Project Command Centre or Executive Overview.
- Slack DM ingestion remains separately excluded by OQ-002. Brain-native DM policy is OQ-008.
- Group DMs, external users and participant-scoped AI over DMs are outside this first slice.

## Backend acceptance

1. Member A creates a DM to exact email for Member B; the response identifies B as the other participant.
2. Member B creates a DM to Member A and receives the same conversation ID; duplicate reverse conversations cannot exist.
3. Self-DM creation is rejected.
4. A target outside the organisation is indistinguishable from an unavailable target.
5. A Guest/read-only target cannot be added to a writable DM.
6. Participant A and B can list/read the conversation.
7. Nonparticipant Owner, Admin and Executive cannot read guessed conversation IDs; return 404/no content.
8. Nonparticipant conversation listing does not expose DM names/participants.
9. Message writes require a participant plus `native_chat.write` organisation capability.
10. Idempotency-Key replay returns the same message without duplicate storage.
11. Message length is bounded at 20,000 characters.
12. Latest bounded history is returned chronologically.
13. Database composite FK prevents cross-tenant conversation/message attachment.
14. Sending DM messages does not increase RawEvent, CanonicalEvent or SearchDocument counts.
15. Audit metadata contains IDs/hash/count only; plaintext message body is not copied into security audit metadata.
16. Migration `20260916_0022` upgrades and downgrades cleanly on PostgreSQL.

## Frontend/BFF acceptance

1. Direct messages appears as its own Slack-style workspace navigation group.
2. A DM is selected only by a `dmId` found in the server-returned participant conversation list.
3. Guessed/unavailable `dmId` renders no private message content.
4. New DM uses exact member email and a same-origin WorkOS BFF route.
5. Send uses same-origin WorkOS BFF plus bounded JSON and an Idempotency-Key.
6. Browser code never receives or constructs a reusable WorkOS/FastAPI bearer token.
7. Both mutation routes reject cross-site/cross-origin requests.
8. DM panel visibly states that content is participant-only and excluded from organisation-wide intelligence.
9. Desktop and narrow/mobile layouts remain usable with keyboard-visible controls.
10. Session expiry and membership removal prevent subsequent DM access without requiring client-side revocation logic.

## Explicit negative tests

- Owner who is not a participant cannot open Member A/B DM.
- Executive who is not a participant cannot open Member A/B DM.
- Cross-tenant user cannot create/read/send into the DM.
- Browser cannot submit arbitrary participant IDs; creation accepts only exact target email and server resolves the current organisation member.
- DM service must not import or call RawEvent/CanonicalEvent/SearchDocument projection functions.
- Ask Brain/Search queries must not return a unique phrase that exists only in a DM.
