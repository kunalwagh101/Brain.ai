# UAT — F-10.04 Production frontend authentication and BFF

Status: **PENDING / EXTERNAL EXECUTION REQUIRED**

Story: `S-10.04.01 — Connect the Next.js workspace to Brain through official WorkOS AuthKit server sessions`

This UAT is the production-browser security gate. Source templates, successful compilation or package installation alone do not satisfy it.

## Installation / activation prerequisites

1. Run `bash scripts/install-workos-authkit.sh` with working npm registry access.
2. Confirm `package.json` and `package-lock.json` contain official `@workos-inc/authkit-nextjs` and `@workos-inc/node` packages with real resolved URLs and integrity hashes.
3. Keep `@workos-inc/authkit-nextjs` on the reviewed 4.x line until a separately reviewed SDK-major upgrade is approved.
4. Configure without committing secrets:
   - `WORKOS_CLIENT_ID`
   - `WORKOS_API_KEY`
   - `WORKOS_COOKIE_PASSWORD` (>=32 characters)
   - `NEXT_PUBLIC_WORKOS_REDIRECT_URI`
   - `BRAIN_API_BASE_URL`
5. `NEXT_PUBLIC_WORKOS_REDIRECT_URI` must point exactly to `/auth/callback`; production must use HTTPS and contain no query string, URL credentials or fragment.
6. Production `BRAIN_API_BASE_URL` must use HTTPS and contain no URL credentials or fragment.
7. Configure the WorkOS dashboard redirect URI to exactly match `NEXT_PUBLIC_WORKOS_REDIRECT_URI`.
8. Configure the WorkOS Initiate login URI to Brain's `/sign-in` route and configure the default sign-out URI.
9. Confirm root `proxy.ts` uses official `authkitProxy()` and its matcher includes both `/` and `/api/brain/:path*`; every route that calls `withAuth()` must be covered by AuthKit proxy execution.
10. Configure the Brain backend with the same trusted WorkOS client/issuer/JWT-template contract in `docs/WORKOS_FRONTEND_ACCEPTANCE.md`.
11. Run `node --test tests/workos-authkit-contract.test.mjs` before activation.
12. Run `bash scripts/activate-workos-authkit.sh` and retain lint/build/test output.

## Authentication scenarios

### 1. Unauthenticated root

Open `/` in a clean browser session.

Pass only if the protected workspace goes through official AuthKit sign-in and no company data is rendered before authentication.

### 2. Callback / session establishment

Complete hosted AuthKit sign-in through `/sign-in` and `/auth/callback`.

Pass only if:

- the dashboard redirect URI, `NEXT_PUBLIC_WORKOS_REDIRECT_URI` and actual callback path match exactly;
- PKCE/state verification succeeds through the official SDK;
- callback URL no longer contains tokens after completion;
- a protected encrypted session cookie is established;
- no access/refresh token is placed in localStorage/sessionStorage;
- internal `x-workos-*` session headers are not reflected to the browser.

### 3. WorkOS token -> Brain identity

Using a real session, load the workspace.

Pass only if FastAPI accepts the signed WorkOS token for the expected client/issuer/email-claim contract and resolves exactly one Brain user. Wrong client, issuer, expiry, malformed token or missing required email claim must fail closed.

### 4. Organisation switching

Use a user who belongs to two Brain organisations.

1. Switch organisations through the workspace picker.
2. Confirm each selection is present in the server-returned membership list.
3. Manually alter `organizationId` to an organisation the user cannot access.

Pass only if the third case returns the unavailable boundary and no target-organisation fields are disclosed.

### 5. Same-origin BFF coverage

Confirm the activated `proxy.ts` matcher covers `/api/brain/:path*` before exercising any BFF mutation. Then inspect browser requests for Ask Brain, Evidence, native channels/conversation UX, DMs, Agent Workspace and Admin Center.

Pass only if every protected BFF route:

- executes through the AuthKit proxy and can successfully call server-side `withAuth()`;
- browser sends no Brain/WorkOS bearer token;
- BFF obtains the access token server-side;
- BFF confirms current Brain organisation membership before forwarding;
- request size/content-type/action validation happens before protected backend mutation/provider invocation;
- upstream failures return bounded status/message without raw backend/provider/secret detail;
- no WorkOS internal session header is reflected to the browser.

### 6. Ask Brain same-origin BFF

Inspect the browser network request to:

`POST /api/brain/organizations/{organizationId}/ask-brain`

Pass only if:

- browser sends no Brain/WorkOS bearer token;
- BFF obtains the access token server-side with WorkOS `withAuth()`;
- BFF confirms organisation membership before forwarding;
- non-JSON and oversized requests fail before provider invocation;
- invalid fields fail with bounded `400`;
- unavailable organisation fails with bounded `404`;
- upstream errors return bounded status/message without raw backend/provider/secret detail;
- successful response contains only the Ask Brain response contract.

### 7. Session expiry and logout

1. Exercise normal `signOut()` through the server action.
2. Revisit the protected root.
3. Where practical, exercise an expired/revoked session.

Pass only if company data is no longer available and the user is required to authenticate again. Configure and verify the WorkOS default sign-out URI.

### 8. Browser secret inspection

Inspect HTML, client JS configuration, network URLs, localStorage, sessionStorage and visible errors.

Pass only if none contains:

- WorkOS access/refresh tokens;
- WorkOS API key;
- cookie-encryption password;
- Brain backend bearer tokens;
- AWS/OpenAI/provider credentials or secret references.
