# UAT — F-10.03 Live intelligence surfaces

Status: **PENDING**

Story: `S-10.03.01 — Use Ask Brain, projects, decisions/blockers and company pulse inside the workspace`

This UAT proves that Brain intelligence is part of the company workspace rather than a disconnected executive dashboard. Backend implementation or component existence alone is not acceptance evidence.

## Preconditions

- S-05.01 permission-aware retrieval has executable passing evidence.
- S-05.02 Ask Brain backend is configured with an approved governed runtime.
- S-04.02 decision/blocker memory has representative confirmed and candidate records.
- S-07.01 Project Command Centre contains at least two visible projects with structured work/evidence.
- S-07.02 Executive Overview is available to an Owner/Admin/Executive account.
- S-10.04 official WorkOS/BFF path is active for the Ask Brain browser mutation.
- Use at least one normal Member/Manager account and one Owner/Admin/Executive account.
- Use at least one restricted project/evidence source that the normal account cannot access.

## Acceptance scenarios

### 1. Normal member workspace

1. Sign in as Member/Manager.
2. Open the Brain workspace.
3. Confirm visible tracks/projects use live tenant data.
4. Confirm Project Command Centre data renders for permitted projects.
5. Confirm confirmed decisions/blockers render with evidence identifiers.
6. Confirm the company-wide Executive Overview is not rendered when the role lacks `audit.read`.
7. Confirm lack of executive permission does **not** block the rest of the workspace.

Pass only if no hidden project name, count, blocker, decision or evidence identifier leaks through navigation, summary cards or context rails.

### 2. Executive/company pulse

1. Sign in as Owner/Admin/Executive.
2. Confirm Company Pulse renders live S-07.02 values.
3. Reconcile visible project count with S-07.01 for the same account.
4. Reconcile confirmed blockers/decisions with the underlying memory records.
5. Reconcile known AI spend and incomplete-cost state with S-06.02.
6. Reconcile budget-warning count with visible budget policies only.

Pass only if the UI preserves unknown/incomplete cost explicitly and never converts missing data into zero.

### 3. Project evidence drill-down

For at least one project:

1. Expand `Structured work & evidence`.
2. Confirm structured work state/weight matches S-07.01.
3. Confirm evidence title/provider/object type/canonical event refer to real permitted evidence.
4. Revoke/remove the test user's permission to one linked restricted evidence source.
5. Refresh.

Pass only if the restricted evidence disappears and project metrics do not reveal hidden evidence through stale counts or labels.

### 4. Decision/blocker provenance

1. Open one confirmed blocker and one confirmed decision.
2. Expand their evidence details.
3. Verify canonical-event/search-document/work-graph identifiers against backend records.
4. Confirm a machine candidate is not presented as a human-confirmed executive fact.

### 5. Ask Brain browser flow

1. Ask a question that has sufficient authorised evidence.
2. Verify the answer contains claims and server-issued citations.
3. Expand each citation and reconcile evidence/provider/object/canonical/search identifiers.
4. Ask a question with insufficient authorised evidence.
5. Confirm the explicit no-answer/uncertainty state.
6. Exercise provider failure/rate-limit/session-expiry behavior.

Pass only if the browser uses the same-origin BFF, no reusable bearer token appears in browser storage/HTML/URLs, raw backend/provider error bodies are not reflected, and permissions are never widened on retry/error.

### 6. No employee scoring

Inspect the authenticated UI and network responses. Pass only if there is no employee productivity/worth/performance score and activity/commit/message/token counts are not transformed into a person ranking.

### 7. Accessibility/responsive

Verify keyboard-only navigation, visible focus, skip link, organisation switcher, expandable evidence/citations, screen-reader labels, 1280px desktop, tablet and small-mobile layouts.
