# F-10.09 Activity & Notification Center UAT

Story: `S-10.09.01`

Status: implementation in progress. No PASS/DONE claim is valid until backend execution, PostgreSQL migration checks, official WorkOS activation and authenticated multi-user browser UAT all pass.

## Product contract

Brain Activity is a personal attention queue, not a second copy of company/private content.

- First slice covers exact mentions, thread replies, reactions and Brain-native direct messages.
- Notifications persist recipient/event/resource references and read state; they do not persist message body, excerpt or copied private content.
- Every Activity read re-checks current access to the referenced channel/DM before returning the item.
- Restricted-channel or DM access revocation removes the item from the visible inbox immediately without needing to delete the immutable notification row.
- Owner/Admin/Executive roles do not gain DM Activity visibility unless they are the DM participant.
- Mark-read state is personal and cannot be mutated by another member.
- Agent-approval notifications are reserved by the schema but are not accepted in this first slice until their S-08/S-10.07 approval-resource access contract is implemented.

## Backend acceptance

1. A valid exact mention creates/materializes one recipient notification and repeated Activity reads do not duplicate it.
2. A reply to a user's root thread creates/materializes one thread-reply notification unless the same reply already produced a mention notification for that recipient.
3. A reaction from another user to the recipient's message creates/materializes one notification per message/user/reaction tuple.
4. A DM from the other participant creates/materializes one participant-only notification.
5. Activity API response contains safe event labels/context and deep-link identifiers but no message body/excerpt/body hash.
6. A user never receives a notification created by their own action.
7. Cross-tenant activity is never returned.
8. Restricted-channel revocation makes an already-persisted notification invisible and removes it from unread count.
9. DM participant revocation/role downgrade/visibility-epoch reset makes inaccessible DM notifications invisible.
10. Hidden/revoked rows do not consume the requested visible result limit.
11. `POST /activity/read-all` resolves as the static route and cannot be shadowed by the UUID `/{notification_id}/read` route.
12. Mark-one-read affects only the authenticated recipient; a guessed notification ID owned by another user does not change that recipient's read state.
13. Mark-all-read updates only currently visible unread notifications for the authenticated recipient.
14. Migration `20260918_0025` upgrades/downgrades cleanly after `20260916_0024` and creates no content-copy column.

## Frontend/BFF acceptance

1. Activity is globally reachable from the authenticated Brain workspace and shows a personal unread badge.
2. Activity drawer is usable on desktop and narrow/mobile layouts.
3. Opening an Activity item produces a valid organisation-scoped channel or DM URL with query parameters before the URL fragment.
4. Activity UI never renders copied message text or hidden-resource names.
5. Mark-one and mark-all use same-origin WorkOS BFF routes only.
6. Browser code never receives or constructs a reusable WorkOS/FastAPI bearer token.
7. Both mutation routes reject cross-site/cross-origin requests.
8. Session expiry or organisation membership loss prevents mutations server-side.
9. Keyboard focus reaches Activity trigger, every visible item, Open action and Mark-all-read action.
10. Empty state clearly reports that the user is caught up without implying all company activity is visible.

## Explicit negative tests

- A nonparticipant Owner cannot see another pair's DM notification.
- A revoked restricted-channel member cannot see an old mention/thread/reaction notification from that channel.
- Re-reading Activity cannot create duplicate notification rows.
- Activity persistence must not add `message_body`, `body_preview`, `content` or `excerpt` columns.
- Browser Activity components must not contain Authorization/Bearer/access-token handling.
- `read-all` must not return UUID-validation 422 because of route ordering.
