# F-10.09 Activity & Notifications Inbox UAT

Story: `S-10.09.01`

Status: implementation in progress. No PASS/DONE claim is valid until backend execution, PostgreSQL migration checks, frontend gates, official WorkOS activation and authenticated multi-user browser UAT all pass.

## Product contract

Brain Activity is one personal attention queue. It stores references and read state, not copies of private/company content.

The inbox must cover:

- exact `@mentions`;
- thread replies;
- unread Brain-native channel activity;
- Brain-native direct messages already supported by the workspace;
- governed agent approval requests;
- agent completion/failure events for the requester;
- visible project progress and blocker updates;
- integration degraded/error/revoke-failed events for members authorised to manage integrations;
- personal read/unread state;
- per-user notification preferences;
- direct links to the exact message/thread/channel, agent run/step, project/blocker or integration surface.

Notification preferences suppress presentation/materialisation for the disabled category without deleting underlying product state. Re-enabling a category must not weaken source permissions.

Every inbox read re-checks current source access. A persisted reference must become invisible immediately when channel, DM, project, agent context, organisation membership or management permission is revoked.

## Backend acceptance

1. A valid exact mention materialises one recipient item and repeated reads do not duplicate it.
2. A reply to a user's root thread materialises one thread-reply item unless the same reply already produced a mention item for that recipient.
3. Reactions and participant-only DMs preserve the existing Activity behaviour and privacy boundary.
4. A readable channel with messages newer than the user's monotonic read cursor produces one channel summary pointing to the latest unread message; a targeted mention/thread item for the same message wins over the generic channel summary.
5. Marking the channel read makes its generic unread-channel item invisible without deleting source messages.
6. A waiting agent step is visible as an approval request only to a user who currently has `agent.manage` and can still see the run context.
7. A completed/failed agent run is visible to the requester only while the requester can still see the run context.
8. Visible project progress updates and confirmed/resolved blocker updates appear only when the current user can still read their Work Graph context.
9. Integration degraded/error/revoke-failed items are returned only to users with current `integration.manage` permission.
10. Integration recovery or permission loss makes an old integration-failure item invisible.
11. Activity API response contains safe labels/context and identifiers only; it contains no message body, DM body, provider secret, API key, agent arguments/result content, project private evidence excerpt or integration external-account secret.
12. Cross-tenant activity is never returned or mutated.
13. Restricted-channel revocation makes persisted mention/thread/reaction/channel items invisible and removes them from unread count.
14. DM participant revocation/visibility reset makes inaccessible DM items invisible.
15. Hidden/revoked rows do not consume the requested visible result limit.
16. `POST /activity/read-all` cannot be shadowed by the UUID `/{notification_id}/read` route.
17. Mark-one-read affects only the authenticated recipient and only a currently visible item.
18. Mark-all-read updates only currently visible unread items for that recipient.
19. `GET /activity/preferences` returns tenant/user-scoped defaults with all supported categories explicit.
20. `PUT /activity/preferences` accepts only the reviewed boolean keys, rejects unknown/empty payloads and cannot update another user's row.
21. Disabled preferences remove that category from the inbox/unread count without deleting the underlying product object.
22. Chat deep links carry `channelId`/`messageId` and `threadRootId` where relevant; DM links carry conversation/message IDs; agent links carry run/step IDs; project/blocker and integration links carry exact source IDs.
23. Alembic has one head after the `0025` notification branch merge; migration `20260918_0027` upgrades/downgrades the inbox extension without content-copy columns.

## Frontend/BFF acceptance

1. Activity is globally reachable from the authenticated Brain workspace and shows a personal unread badge.
2. Drawer is usable on desktop and narrow/mobile layouts.
3. All required event categories render with understandable labels and an Open action.
4. Opening an item routes to the exact permitted source context, not only a generic workspace page.
5. Notification preferences are keyboard-accessible labelled controls and save through the same-origin BFF.
6. Mark-one, mark-all and preference mutations use same-origin WorkOS BFF routes only.
7. Browser code never receives or constructs a reusable WorkOS/FastAPI bearer token.
8. Mutation routes reject cross-site/cross-origin requests; preference writes also require bounded JSON.
9. Session expiry or organisation membership loss prevents mutations server-side.
10. Empty state reports that the user is caught up without implying all company activity is visible.
11. Browser/response inspection finds no copied DM text, private message body, secret reference, provider credential or agent tool argument/result content.

## Explicit negative tests

- A nonparticipant Owner cannot see another pair's DM notification.
- A revoked restricted-channel member cannot see an old channel/mention/thread/reaction item.
- A normal Member cannot receive integration-management failure items or agent approval controls merely by guessing IDs.
- An agent approval disappears when the step is no longer waiting for approval or context access is removed.
- An integration-failure item disappears after health recovers.
- Re-reading Activity cannot create duplicate notification rows for stable events.
- A mention/thread message must not also count as a generic channel unread item for the same source message.
- Activity persistence must not add message bodies, excerpts, credentials, tool arguments or results.
- Browser Activity components must not contain `Authorization`, `Bearer`, WorkOS/FastAPI access-token or browser-storage token handling.
- Unknown preference keys and non-boolean values fail closed.
- `read-all` must not return UUID-validation `422` because of route ordering.
