# UAT F-05.01 — Permission-Aware Retrieval

Status: `UAT_PENDING`

Engineering tests are intended to prove deterministic authentication, tenant/RBAC/ACL behaviour, projection idempotency, revocation handling and hybrid-search fallback. Production acceptance still requires real WorkOS authentication, realistic Slack/GitHub data, PostgreSQL + pgvector, a configured embedding endpoint, and the real frontend/manual workflow.

## Acceptance layers

S-05.01 is not accepted from any one layer alone. Required evidence is:

1. local acceptance-runner contract + Ruff + first-stage pytest passes;
2. Render staging image build passes the portable ordered acceptance chain through S-05.01;
3. Render startup runs the same first-stage contracts against an isolated schema on real managed PostgreSQL/pgvector and passes before Uvicorn becomes healthy;
4. a real WorkOS AuthKit access token is accepted/rejected according to the production identity contract;
5. realistic staging permission/revocation/recall/latency UAT below passes;
6. frontend/manual validation passes when the official AuthKit frontend path exists.

A GitHub Actions job that fails before any workflow step executes is not a test failure and is not a PASS.

## Render executable gate

Free Render web services do not provide the interactive execution path this acceptance depends on, so the checked-in staging image/start command runs it automatically.

`backend/Dockerfile.staging` runs the acceptance-runner contract, Ruff and the ordered portable backend chain during image build. Then `render.yaml` performs:

```text
alembic upgrade head
BRAIN_TEST_DATABASE_URL="$BRAIN_DATABASE_URL" \
  python run_acceptance_chain.py \
    --require-postgres \
    --report /tmp/brain-acceptance-postgres.json
```

before Uvicorn starts. The ordered chain begins with S-05.01 and stops immediately if it fails, so no downstream story can acquire a misleading backend PASS marker.

When `BRAIN_TEST_DATABASE_URL` is present, the pytest fixture creates a unique temporary PostgreSQL schema, verifies PostgreSQL + pgvector + active search-path isolation, runs through PostgreSQL code paths and drops only that temporary schema afterward. Normal staging application data is not used as test fixture data.

Capture from Render:

- deployed `RENDER_GIT_COMMIT`;
- acceptance-runner contract result;
- image-build Ruff result;
- portable first-stage result;
- migration-to-head result;
- runtime PostgreSQL/pgvector first-stage result;
- `/health/ready` result after the chain passes.

A healthy deployment without the relevant logs is not sufficient evidence.

## Real WorkOS authentication validation

Brain's production authentication boundary must be exercised with the same WorkOS application used by the official frontend.

Preconditions:

- `BRAIN_WORKOS_CLIENT_ID` equals the WorkOS application client ID;
- standard AuthKit tokens use `client_id`; leave `BRAIN_WORKOS_AUDIENCE` unset unless an explicit custom `aud` claim is intentionally configured;
- exact trusted issuer is configured (`BRAIN_WORKOS_ISSUER` when it differs from the default);
- WorkOS JWT Template includes:

```json
{
  "urn:brain:user_email": {{ user.email }}
}
```

Brain deliberately does not use optional `act.sub` as the signed-in user's email.

Verify with real staging tokens/sessions:

1. valid AuthKit token with matching `client_id`, issuer, unexpired signature and `urn:brain:user_email` reaches `/api/v1/auth/me` successfully;
2. wrong application/client token fails closed;
3. wrong issuer fails closed;
4. expired/malformed token fails closed;
5. token missing `urn:brain:user_email` fails closed;
6. if impersonation/delegation is tested, actor context never replaces the stable subject/email mapping;
7. no access token, refresh token, WorkOS API key or encrypted AuthKit session payload is copied into Git evidence.

See `docs/WORKOS_FRONTEND_ACCEPTANCE.md` for the browser/session/BFF half of this contract.

## Real-data backend validation

Prepare at least:

- one authorised public Slack channel with searchable messages;
- one authorised private Slack channel with two test members;
- one private Slack member removed during the test;
- one public GitHub repository;
- one restricted/private GitHub repository;
- one explicit `github.repository` READ grant and one user without that grant;
- a second Brain organisation for cross-tenant negative tests;
- one source object that can be deleted or made unavailable;
- at least ten labelled search questions with known relevant evidence.

Verify:

1. migrations are at `head` and vector/search tables/indexes exist;
2. historical canonical events project without duplicates;
3. embeddings unconfigured/unavailable still permit keyword projection;
4. Org A search returns no Org B identifiers/content/provenance;
5. an unauthorised public Slack channel remains absent until explicitly authorised;
6. a private Slack result appears only for a Brain user currently resolved to a listed Slack channel member;
7. removing membership/authorisation removes that result on the next query;
8. private/internal GitHub evidence is absent even for Owner/Admin without a matching resource grant;
9. adding READ grant makes that evidence searchable;
10. revoking the integration hides its evidence without deleting raw/canonical audit evidence;
11. canonical/source deletion removes or hides derived retrieval content;
12. labelled keyword/hybrid retrieval recall is measured;
13. semantic retrieval can find relevant evidence without exact query-term overlap;
14. embedding outage degrades hybrid search to keyword results with `semantic_status=degraded`;
15. every result contains canonical event ID, provider, source/object reference, timestamp and provenance;
16. embedding/provider secrets remain secret-reference only and absent from logs/rows returned to users;
17. concurrent worker batches do not commit duplicate document/embedding work;
18. p50/p95 keyword and hybrid search latency is measured at representative dataset size;
19. disposable downgrade/forward migration leaves raw/canonical evidence sufficient to rebuild retrieval.
