# F-10.08 Workspace Admin & Governance UAT

Story: `S-10.08.01`

Status: implementation in progress. No PASS is claimed until executable backend checks plus authenticated browser UAT complete.

## Scope

The Brain workspace provides an Owner/Admin-only administration surface for:

- organisation members and roles;
- integration lifecycle/health;
- AI provider/model creation, credential rotation and status governance;
- external API service/grant creation, ownership, scopes, environment, credential rotation, expiry and usage state.

The frontend must use authoritative backend permission checks. Browser code must never receive stored credential values, secret references, provider tokens or reusable Brain bearer tokens. Newly typed secrets may exist only transiently in the active form/request and must be cleared after success.

## Backend acceptance

1. Owner can read `/api/v1/organizations/{organization_id}/admin-center`.
2. Admin can read the same aggregate.
3. Manager/member/executive/guest cannot read the privileged aggregate unless their backend permissions are explicitly changed in a reviewed policy update.
4. Cross-tenant access returns no target organisation data.
5. Response includes safe member identity/role, integration status/health, AI provider/model status and API grant governance metadata.
6. Response never serializes `secret_ref`, raw credential dictionaries, API keys, OAuth tokens or integration external-account secrets.
7. `credential_present` is boolean metadata only.
8. Counts reconcile exactly with the visible aggregate rows.
9. Owner can assign Owner/Admin and regular roles.
10. Admin can manage regular roles but cannot assign, demote or remove Owner/Admin memberships.
11. The final Owner cannot be demoted or removed; both mutations must return `409`.
12. Removing an organisation membership deletes that user's organisation `ResourceGrant` rows and revokes active restricted-channel and Brain-native DM participation so re-adding the user cannot silently restore stale access.
13. Membership create/role/remove mutations produce security-audit evidence without copying private DM content.
14. Integration revocation must transition through the existing secret-deletion lifecycle and never return stored credentials.
15. Owner/Admin can create an AI provider only through `ai.manage`; credential storage produces only a secret reference in Brain persistence.
16. Owner/Admin can add a governed model to a mutable provider; model status remains backend-authoritative.
17. AI provider credential rotation uses in-place secret replacement, updates `credential_rotated_at`, never changes the provider identity, and never echoes the credential. Secret-store failure returns a safe failure and does not claim rotation success.
18. Revoking/revoked AI providers cannot rotate credentials.
19. Owner/Admin can create an external API service and then create a grant owned by an active organisation member.
20. API grant creation stores credentials only in the secret store; Brain persists only the reference/governance metadata.
21. Grant owner, scopes and environment mutations use the existing registry history model and reject revoked/expired grants where the registry contract says metadata is immutable.
22. API grant credential rotation uses secret replacement plus `credential_rotated_at`/history and never echoes credential content.
23. API grant enable-disable/revoke remains enforced by `api.manage`; revocation removes the stored grant credential through the existing registry lifecycle.

## Frontend acceptance

1. Owner/Admin sees `Admin & governance` in the Brain workspace navigation.
2. Other roles do not trigger the privileged Admin Center backend request and do not see the navigation item.
3. Member/role list matches the backend aggregate.
4. Owner sees Owner/Admin choices; Admin cannot use the UI to mutate protected Owner/Admin memberships.
5. Add-member, role-change and remove-member actions use only the same-origin Admin Center route.
6. Destructive member removal requires explicit browser confirmation.
7. Integration health and error state match backend data, and integration revoke requires explicit confirmation.
8. An empty organisation can create its first governed AI provider without direct API/database work.
9. Provider creation accepts only the reviewed adapter(s), URL and transient credential input; after success the secret input is cleared and cannot be redisplayed.
10. A mutable provider can add a model and rotate its credential; revoked/revoking providers do not present valid mutation controls.
11. API service creation works from the Admin Center even when no registry service existed beforehand.
12. API grant create requires service, key, name, active owner, environment, scopes and credential JSON; optional expiry is validated by the backend.
13. API grant owner, environment, scopes, expiry, credential-present state and usage count match backend data.
14. Owner/scopes/environment edits refresh from authoritative backend state after success.
15. API grant credential rotation accepts transient JSON only, clears the field after success and never re-renders the stored credential.
16. API grant enable-disable and revoke use the same-origin route; revoke requires explicit confirmation.
17. No stored secret value is visible in rendered HTML, server component data, browser storage or mutation success responses.
18. Browser admin code never constructs an `Authorization` header or receives a reusable Brain/WorkOS bearer token.
19. Admin Center does not use `localStorage`, `sessionStorage` or IndexedDB for secret/admin mutation persistence.
20. Admin Center remains usable on desktop and narrow/mobile layouts.
21. Keyboard navigation and focus order cover Admin navigation plus all member/integration/AI/API mutation controls.
22. After every successful mutation, the UI refreshes from the authoritative server response rather than relying on an optimistic local permission state.

## Same-origin BFF acceptance

The reviewed WorkOS activation creates exactly one Admin Center mutation endpoint:

`POST /api/brain/organizations/{organization_id}/admin-center/actions`

The route must:

- require a real WorkOS `withAuth()` session and server-side access token;
- enforce `application/json` and a 32 KiB request ceiling;
- reject cross-site/cross-origin mutation attempts;
- accept only the reviewed discriminated action contract;
- bound credential objects to 1-16 string fields, each field name <=128 chars and each value <=8192 chars;
- revalidate current Brain organisation membership and Owner/Admin role before forwarding;
- keep raw FastAPI/provider/secret-store error details out of browser responses;
- preserve safe upstream HTTP statuses only;
- never serialize stored credentials, secret references or tokens.

Current allow-listed actions are:

- `member_invite`, `member_role`, `member_remove`;
- `integration_revoke`;
- `ai_provider_create`, `ai_provider_status`, `ai_provider_rotate`, `ai_provider_revoke`;
- `ai_model_create`, `ai_model_status`;
- `api_service_create`;
- `api_grant_create`, `api_grant_owner`, `api_grant_scopes`, `api_grant_environment`, `api_grant_rotate`, `api_grant_status`, `api_grant_revoke`.

## Explicit negative tests

- Member/Manager/Executive cannot call Admin Center or provider/API mutation endpoints through role spoofing.
- Admin cannot assign/remove Owner/Admin memberships where Owner authority is required.
- Final Owner cannot be demoted/removed.
- Cross-tenant membership/provider/service/grant IDs expose no target metadata.
- AI provider rotation after revocation starts is rejected.
- Secret-store rotation failure does not update `credential_rotated_at` or return the attempted secret.
- Revoked/expired API grants cannot be silently re-enabled or rotated.
- Invalid owner IDs, malformed scopes/environment, malformed credential JSON and over-32-KiB action bodies fail closed.
- Refresh/reload after a credential mutation never repopulates a secret-entry input.
- Browser storage inspection finds no credential value, secret reference, WorkOS access token or Brain bearer token.
