## 1. Migration and PostgreSQL immutability

1. Run `alembic upgrade head` from revision `20260907_0013`.
2. Confirm revision `20260908_0014` is current.
3. Create one audit event through a supported security/governance action.
4. Attempt a direct SQL `UPDATE security_audit_events ...` against that row in the test database.
5. Confirm PostgreSQL rejects the update with the append-only trigger.
6. Confirm normal retention-controlled `DELETE` remains possible when policy makes an audit row eligible.
7. Exercise downgrade in a disposable database and then upgrade again.

Expected: schema upgrade/downgrade is clean; UPDATE is rejected; no claim is made that downgrade restores previously deleted customer data.

## 2. Permission boundary

Using the actual API/UI:

- Owner: can read and change policy, create/execute deletion and read audit history.
- Admin: same governance-management capability.
- Executive: can read policy/audit/history but cannot change policy or execute deletion.
- Member: cannot read organisation-wide audit/governance data and cannot mutate it.
- Cross-tenant IDs must never return another organisation's policy, deletion or audit record.

Confirm denied governance mutations create a durable `authorization.denied` audit event where persistence is available.

## 3. Retention policy default

For a newly created organisation with no configured retention policy:

1. Run the governance worker.
2. Confirm no raw/derived/audit rows are age-purged merely because they are old.

Then create a policy with each duration left `NULL` and repeat.

Expected: unset means no automatic age-based purge. Brain does not invent a retention duration.

## 4. Derived retention

Prepare a realistic old Slack message or GitHub object that has:

- raw event
- canonical event
- search document
- any Work Graph projection
- decision/blocker candidate if applicable

Configure `derived_content_days` so it is eligible while `raw_event_days` remains unset.

Run:

```bash
python -m app.data_governance_worker --once --batch-size 100
```

Verify directly in PostgreSQL/API:

- raw event remains;
- canonical event is gone;
- search result is gone;
- Work Graph evidence derived from that canonical event is gone;
- decision/blocker derived evidence is gone;
- a derived-retention tombstone exists;
- tombstone contains only raw-event ID + provider/object locator + purge time, not message/document content.

Then invoke canonical reconciliation/replay for the retained raw event.

Expected: purged derived content is not rebuilt.

## 5. Source-object deletion after derived retention

Using the object from step 4:

1. Create a source-object deletion request using provider, object type and object external ID.
2. Execute the request.
3. Confirm the retained raw event is deleted even though the canonical row was already removed.
4. Confirm the deletion record reports the raw deletion count and a completion digest.
5. Confirm the tombstone disappears through raw-event cascade.

Expected: no raw evidence remains for that target and no deleted content is copied into the completion record.

## 6. Normal source-object deletion and replay suppression

Prepare another current source object with raw + canonical + search/graph derived evidence.

1. Create/execute source-object deletion.
2. Confirm raw, canonical, search and dependent derived evidence disappear.
3. Replay/redeliver the same source object through the connector test path using a different delivery/event ID.
4. Run canonical/search/work-graph reconciliation.

Expected: the deleted source object does not reappear.

## 7. Integration deletion

1. Attempt to create an integration deletion request while the integration is ACTIVE.
2. Confirm it is rejected.
3. Revoke the integration through the governed integration lifecycle and wait for fully `revoked` state.
4. Create and execute an integration deletion request.
5. Confirm all active raw/canonical/derived evidence for that integration is removed.
6. Confirm another organisation's integration ID cannot be targeted.

Expected: deletion cannot bypass revocation or tenant boundaries.

## 8. Legal hold

1. Enable `legal_hold=true`.
2. Make raw/derived/audit rows old enough to qualify for configured retention.
3. Run retention.
4. Confirm zero eligible customer evidence is purged.
5. Attempt to create a new deletion request and execute an already-existing pending request.
6. Confirm both operations are blocked while the hold is active.
7. Disable legal hold through the governed policy API.
8. Confirm the policy change is audited, then rerun the approved deletion/retention operation.

Expected: legal hold wins until explicitly removed.

## 9. Audit retention

Create old and recent security audit events in the test organisation. Configure `audit_event_days` so only the old event is eligible.

Run retention and verify:

- only eligible old audit rows are removed;
- recent audit rows remain;
- retention-run control record remains;
- the completion audit record is newly written;
- no other tenant's audit rows are affected.

## 10. ACL audit atomicity

Through the normal resource-grant API:

1. create a resource grant and verify the corresponding durable ACL audit row exists;
2. delete the grant and verify the deletion audit row exists;
3. in a controlled disposable environment, force audit persistence to fail and confirm the ACL mutation does not quietly succeed.

Expected: security mutation and required audit evidence are fail-closed together.

## 11. Worker recovery and concurrency

1. Put a deletion request in `processing` with `started_at` older than 15 minutes.
2. Run the worker and confirm it is retried through the idempotent executor.
3. Start two worker instances against PostgreSQL with several eligible rows.
4. Confirm no request is double-counted and no customer row is incorrectly deleted twice.
5. Record worker completion/failure counts and database lock behavior.

## 12. Frontend/manual workflow

Using the real application UI once the governance UI exists:

- view current retention policy;
- edit raw/derived/audit durations;
- enable/disable legal hold;
- create a typed deletion request;
- show clear target/scope/reason before execution;
- show pending/processing/completed/failed state;
- show deletion counts and completion digest, not deleted content;
- show audit/retention history to authorised roles;
- verify loading, empty, validation, permission-denied, legal-hold and failure states.

If the production frontend for F-09.02 does not yet exist, record frontend/manual as PENDING. Do not substitute Swagger or database inspection for frontend acceptance.
