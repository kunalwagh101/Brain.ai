## Real-data backend validation

1. Run `alembic upgrade head` and confirm revision `20260907_0013` applies cleanly.
2. Register one real non-production external API service through `POST /api-registry/services`.
3. Register a credential grant owned by a real active member with realistic scopes, environment and expiry.
4. Inspect PostgreSQL directly and confirm the grant row contains only a secret reference; no API key/token/client secret appears in registry/history/usage tables.
5. Inspect the configured secret manager and confirm the credential exists in the dedicated `api-credentials/<org>/<service>/<grant>` namespace.
6. Read the grant through the API and confirm only `credential_present` is returned; no secret reference or credential value is exposed.
7. Attempt the same service/grant from a second organisation and confirm cross-tenant reads/mutations return no foreign fields.
8. As a normal Member, confirm registry reads are denied. As Executive, confirm read access but mutation denial. As Owner/Admin, confirm mutation access.
9. Reassign the grant to another active same-org member and confirm immutable history contains old/new owner and actor/reason.
10. Narrow scopes and change environment. Confirm immutable history contains exact before/after metadata without any credential material.
11. Rotate the real test credential. Confirm the secret value changes in the secret manager, the PostgreSQL secret reference remains unchanged, `credential_rotated_at` changes and history contains only rotation metadata.
12. Disable the grant and confirm compliant calling code refuses to use it. Re-enable before expiry and confirm normal state returns.
13. Force secret-deletion failure in a controlled test environment and revoke. Confirm status becomes `revoke_failed`, cannot be re-enabled/rotated/metadata-mutated, and no caller uses it.
14. Restore secret deletion and retry revoke. Confirm status becomes `revoked`, `secret_ref` becomes NULL and history preserves start/failure/retry/success sequence.
15. Create a second short-lived test grant. Let its expiry pass and run:

```bash
cd backend
python -m app.api_registry_worker --once --batch-size 100
```

16. Confirm the grant becomes `expired`, one expiry history event exists, and secret deletion is scheduled. Re-run the worker and confirm expiry/history is idempotent.
17. Simulate one secret-cleanup failure for an expired grant. Confirm it stays `expired` and unusable, the reference remains only for cleanup retry, and the next successful worker run clears it.
18. Wire one trusted test caller to `record_api_usage(...)` and make at least three real test calls with deterministic observation IDs.
19. Confirm replay of one observation does not double-count usage.
20. Confirm `usage_count`, `last_used_at`, success/failure and latency match the real calls.
21. Attempt/observe a call after disable/revoke in the controlled test path and confirm it remains visible as security evidence rather than disappearing.
22. Run `alembic downgrade 20260907_0012` in a disposable environment and confirm rollback removes registry tables without altering unrelated integration/AI request evidence.

## Acceptance criteria

PASSED requires all of the following:

- zero cross-tenant leakage
- zero plaintext credential persistence or response exposure
- same-org active ownership enforcement
- immutable lifecycle history verified
- fail-closed revocation and expiry verified
- rotation verified against the real secret manager
- expiry cleanup retry verified
- usage observation idempotency verified against real calls
- frontend/manual workflow accepted
