# UAT — F-10.07 Developer & Agent Workspace

Story: `S-10.07.01`.

Status: **BLOCKED / NOT PASSED**. Repository automation is green, but official WorkOS activation and authenticated browser UAT below have not been executed.

## Preconditions

- PostgreSQL migrations are at head, including `20260916_0021`.
- Official WorkOS AuthKit is installed and production frontend activation succeeded.
- Test organization has at least two users, one visible project, one restricted project, one organization channel and one restricted channel.
- At least one enabled governed agent has `search.query` and one `act_with_approval` high-risk tool policy.

## 1. Agent/model/tool identity

1. Open Developer & agents as an authorized Member/Manager/Executive.
2. Confirm every displayed agent matches the backend definition.
3. Confirm provider/model display identity matches configured provider/model.
4. Confirm tool list and policy match S-08.01.
5. Confirm high-risk tool is visibly marked as requiring approval.
6. Confirm no secret reference, API key, credential or bearer token is visible in page HTML, React state/network payloads or browser storage.

Expected: only governed identity/policy metadata is visible.

## 2. Visible project context

1. Start a run against a project the user can currently see.
2. Confirm run context displays that project.
3. For a GitHub-backed project, confirm repository identifier comes from the server project record rather than editable browser text.
4. Attempt to POST a hidden/restricted project UUID by modifying the request.
5. Attempt a project UUID from another tenant.

Expected: visible project succeeds; hidden/cross-tenant project fails with 404-style non-disclosure and creates no workspace run.

## 3. Visible channel context and revocation

1. Grant the user access to a restricted Brain channel.
2. Start a run bound to that channel.
3. Confirm channel name/visibility render.
4. Revoke channel membership.
5. Refresh the existing run.

Expected: run remains in requester history, but revoked channel context is no longer named/rendered. A new run cannot be bound to the revoked channel.

## 4. Requester isolation

1. User A creates several workspace runs.
2. User B in the same organization opens Developer & agents and calls the run-list endpoint.
3. User B attempts User A's run UUID directly.

Expected: User B does not receive User A's run list/details. Executives do not gain another user's private run history merely due role.

## 5. Start and first planning step

1. Select an approved agent and at least one visible project/channel context.
2. Enter an objective and start the run.
3. Confirm the client creates the contextual run and then advances the first governed planning step.
4. Inspect database/API response.

Expected: objective plaintext is not persisted in `agent_runs` or `agent_run_contexts`; hash/character count are present; run/step state matches the runtime.

## 6. Approval-gated action

1. Use an agent whose planner proposes `work_graph.create_work_item` under `act_with_approval`.
2. Confirm UI shows tool name, proposed arguments, policy and `waiting_approval` status before execution.
3. Reject once and verify tool did not execute.
4. Repeat with a fresh run, approve, then continue using the same objective during the live session.
5. Confirm work item is produced only after approval.

Expected: no high-risk action executes before explicit approval. Rejection remains authoritative.

## 7. Objective re-entry after reload

1. Produce a run that is `ready` for another planning step.
2. Reload the browser.
3. Attempt to continue without re-entering the objective.
4. Re-enter the original objective and continue.

Expected: Brain clearly asks for objective re-entry; plaintext objective is not reconstructed from server data.

## 8. Structured artifact integrity

1. Complete an approved `work_graph.create_work_item` step.
2. Confirm Developer & agents displays a work-item artifact with the returned node ID/name.
3. Inspect an agent response that merely mentions a PR/patch in prose but did not run a governed PR/patch tool.

Expected: only tool result metadata becomes an artifact. No fake patch/PR card is created from model prose.

## 9. No arbitrary shell

Inspect UI, frontend source and network actions.

Expected:
- no terminal/shell command execution endpoint;
- no browser repository credential;
- no arbitrary filesystem command input;
- only approved tool actions are exposed;
- direct browser attempts to add model/provider/tool/actor fields are rejected or ignored by exact server contracts.

## 10. Cancel and terminal states

1. Cancel an active requester-owned run.
2. Refresh.
3. Attempt another advance after cancellation.

Expected: cancellation persists and further invalid progression is denied by S-08.01 state rules.

## 11. Responsive/accessibility

Verify desktop/tablet/mobile layouts, keyboard navigation, focus visibility, labels, approval controls and error/status announcements.

Expected: agent controls are operable without mouse-only behavior and no approval action is visually ambiguous.

## PASS criteria

S-10.07.01 may move to DONE only when backend/migration/frontend executable checks and authenticated browser UAT pass, with zero cross-tenant/context leakage, zero browser credential exposure and zero high-risk execution before approval.
