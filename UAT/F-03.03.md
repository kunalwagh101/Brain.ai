## Real-data backend validation

Use at least:

- one Slack human actor observed more than once
- one GitHub human actor observed more than once
- one deliberately unmatched source identity
- one Brain member in a different organisation for a cross-tenant negative check
- where the provider can supply genuinely verified email evidence, one exact same-organisation email match

Verify:

1. a canonical human actor creates a tenant-scoped source identity using the provider and stable external ID
2. repeated events for the same provider actor reuse the same source identity and add separate observations
3. source identities remain distinct from WorkOS authentication identities
4. the original canonical `actor_type`, `actor_external_id` and display evidence remain unchanged after resolution
5. missing or unverified email evidence remains `UNRESOLVED`
6. provider-verified exact email evidence resolves only to an active member of the same Brain organisation
7. an otherwise matching user in a different Brain organisation is never linked
8. contradictory verified evidence moves the source identity to `REVIEW_REQUIRED` and does not retain unsafe attribution
9. Owner/Admin can manually resolve an unresolved identity to an active member in the same organisation
10. Owner/Admin can reassign that identity and the linked canonical events update `resolved_user_id`
11. Owner/Admin can unresolve it and canonical events clear `resolved_user_id` while preserving source actor evidence
12. the resolution history records previous user, new user, action, method, actor and bounded evidence for each material change
13. a normal Member cannot call the identity-management endpoints
14. reconciliation links existing canonical actors to source identities without duplicating observations on replay

## Negative / safety validation

Confirm the system does **not** automatically link identities based on:

- display name alone
- similar usernames
- matching company/email domain alone
- cross-tenant user records
- LLM/model inference
- unverified email supplied as ordinary source metadata

Uncertainty is expected to remain unresolved rather than becoming a guessed attribution.

## Frontend / manual validation

When the identity-management UI is available, verify:

- unresolved identities are clearly labelled as unresolved, not shown as known employees
- provider and source external ID are understandable to an admin
- filtering by provider/state works
- manual resolve, reassign and unresolve flows require an authorised Owner/Admin
- the chosen Brain member is clearly shown before mutation
- resolved state distinguishes deterministic verified resolution from manual resolution
- `REVIEW_REQUIRED` is visibly different from ordinary unresolved state
- history/audit information is accessible to authorised administrators
- loading, empty, permission-denied, validation-error and success states are understandable
