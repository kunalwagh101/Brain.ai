# UAT — F-09.04 Performance and cost budgets

Status: `UAT_PENDING`.

Story: `S-09.04.01 — Enforce measurable latency/cost budgets`.

This UAT must use a real deployed candidate with representative non-sensitive data. Unit-test timing, localhost timing or an empty SQLite database does not satisfy this acceptance.

## Prerequisites

Record:

- tester/operator;
- date/time;
- commit SHA and immutable image digest;
- Performance Gate run URL;
- staging runtime/region;
- API instance CPU/memory/replica count;
- PostgreSQL service/version/size class;
- approximate benchmark data volume;
- benchmark client region;
- benchmark organisation UUID in the private acceptance record;
- search indexed-document count;
- AI provider/model if AI benchmark is enabled;
- configured F-06.02 rate source and effective rate.

Use a dedicated benchmark organisation. Do not run the AI scenario against unrelated live customer spend.

## 1. Core API benchmark

1. Ensure the benchmark user is a valid member of the test organisation.
2. Run the checked-in `core_organization_read` scenario without changing its load parameters.
3. Record request count, concurrency, p50, p95, p99, max latency, throughput and success rate.
4. Confirm p95 is below 500 ms and success rate meets the configured minimum.
5. Repeat three times under materially comparable conditions.

Expected: each accepted baseline run is reproducible and reports the same workload definition. A breach is recorded as a failed/review-required result, not hidden by averaging runs together.

## 2. Permission-aware search benchmark

1. Seed/ingest a representative number of permitted and restricted Slack/GitHub search documents.
2. Confirm functional search permission tests/UAT first: the benchmark must not be used to validate authorization correctness.
3. Use a representative non-sensitive query that returns a stable result set.
4. Run the checked-in `permission_aware_search` scenario.
5. Record p50/p95/p99/throughput/error rate and indexed-document count.
6. Confirm p95 is below 1.5 seconds.
7. Repeat three comparable runs.
8. Inspect PostgreSQL query plan/index use if p95 breaches.

Expected: search stays permission-aware and measured performance is reported against stated data volume. Do not claim customer-scale search performance from a tiny index.

## 3. Governed AI latency and cost

Run only after F-06.01/F-06.02 functional verification and with a budget-limited test organisation.

1. Configure a real test provider/model and an effective exact rate card.
2. Confirm no unrelated AI requests are running in the benchmark organisation.
3. Set `BRAIN_PERF_ENABLE_AI=true` and run the checked-in AI scenario.
4. Record provider/model, p50/p95/p99, success rate and throughput.
5. Confirm p95 is below 10 seconds.
6. Record known cost delta, unknown-cost request delta and cost per successful evaluated task.
7. Confirm `exact_cost_complete=true`; otherwise the benchmark must fail and the accounting gap must be fixed/reconciled.
8. Compare the reported cost delta to the F-06.02 request records/rate calculation.
9. Repeat only as necessary; avoid unnecessary external-provider spend.

Expected: latency and exact measured task cost are both visible. There is currently no made-up maximum cost ceiling; record the baseline for later product-economic agreement.

## 4. Regression proof

In an isolated test branch/environment only:

1. Temporarily set one p95 budget below an already observed healthy p95 or introduce a controlled delay.
2. Run the Performance Gate.
3. Confirm the benchmark exits non-zero and the workflow fails.
4. Restore the correct checked-in budget/code.
5. Re-run and confirm normal result.

Expected: a measured budget breach creates a technical failure/review signal.

Do not permanently loosen the production budget merely to make this step green.

## 5. Report security

Inspect `.performance/report.json` and workflow logs.

Confirm neither contains:

- bearer token;
- API key/OAuth token;
- AI provider credential;
- AI prompt/completion body;
- response bodies/customer content.

Confirm the report contains aggregate metrics and route templates rather than a request-by-request sensitive trace.

Expected: benchmark evidence is useful for engineering review without becoming a secret/content artifact.

## 6. Like-for-like comparison

Take two candidate reports intended for comparison and verify the record includes or separately captures:

- same workload version;
- same request count/concurrency;
- same approximate database/index data volume;
- same API/database size class;
- same benchmark geography/network relationship;
- same AI provider/model for AI comparisons.

If any material dimension differs, label the comparison as confounded rather than claiming a code-only regression/improvement.

## 7. Frontend/manual performance acceptance

From the real staging frontend:

1. sign in as the benchmark test user;
2. load a normal core view backed by the measured API;
3. perform the representative search flow;
4. if AI is enabled in the UI, run one governed AI action/question;
5. inspect loading states, duplicate submissions, timeouts and error behavior;
6. correlate slow/erroring operations with request IDs/telemetry;
7. confirm the UI does not imply success while a request is still pending or failed.

Frontend perception is not a substitute for measured backend p95, but both must be acceptable before final feature acceptance.
