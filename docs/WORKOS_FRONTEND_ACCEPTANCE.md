# WorkOS / frontend acceptance — Brain production path

Status: **IMPLEMENTATION_STAGED / UAT_PENDING**

This document defines the only accepted production authentication/frontend path for Brain. The existing `app/chatgpt-auth.ts` integration is a preview-host helper and is **not** an accepted production authentication mechanism.

## Security boundary

Production browser authentication must use the official WorkOS AuthKit Next.js SDK. Do not replace it with hand-written OAuth, custom PKCE/state handling, copied bearer tokens, localStorage access tokens, or manually fabricated package-lock entries.

The browser must not receive the Brain backend bearer token for ordinary API use. The accepted flow is:

`browser -> WorkOS AuthKit encrypted session cookie -> Next.js server component/BFF -> server-held WorkOS access token -> FastAPI Authorization: Bearer -> Brain permission checks`

`app/brain-api.ts` is the server-side FastAPI client contract. It uses `cache: no-store`, requires an explicit bearer token, refuses non-HTTPS Brain API URLs in production, and never places the token in a URL.

## Frontend environment

Server/private:

```text
WORKOS_CLIENT_ID=client_...
WORKOS_API_KEY=sk_...
WORKOS_COOKIE_PASSWORD=<strong random value, at least 32 characters>
BRAIN_API_BASE_URL=https://<brain-api-staging-or-production-host>
```

Browser-safe:

```text
NEXT_PUBLIC_WORKOS_REDIRECT_URI=https://<frontend-host>/auth/callback
```

The backend separately requires the same WorkOS application client ID:

```text
BRAIN_WORKOS_CLIENT_ID=client_...
```

For standard AuthKit session tokens, leave `BRAIN_WORKOS_AUDIENCE` unset. Brain validates the signed JWT `client_id` against `BRAIN_WORKOS_CLIENT_ID`. `BRAIN_WORKOS_AUDIENCE` is only an optional *additional* custom-audience gate when an operator intentionally configures a token `aud` claim.

If a WorkOS custom auth domain changes the JWT issuer, set `BRAIN_WORKOS_ISSUER` to that exact trusted issuer rather than weakening issuer validation.

## Required WorkOS JWT Template

Brain links the stable WorkOS subject (`sub`) to its internal user and requires an explicit subject-email claim. Do not use the optional `act` actor/delegation claim as the user's email.

Configure the WorkOS AuthKit JWT Template with:

```json
{
  "urn:brain:user_email": {{ user.email }}
}
```

The backend rejects tokens without a usable `urn:brain:user_email` value. This is deliberate fail-closed behavior. The claim is used only for initial safe user linking; `sub` remains the stable WorkOS external identity key.

## Next.js 15 integration

This repository currently uses Next.js 15, so use `middleware.ts`, not the Next.js 16 `proxy.ts` path.

### 1. Protect the production workspace

After the official packages are installed, add `middleware.ts` using `authkitMiddleware` and protect only the application/API paths that need authentication. Do not accidentally intercept static assets.

The WorkOS SDK's middleware helpers must be used as documented so sensitive internal `x-workos-*` session headers are kept server-side and are not reflected to the browser.

### 2. Callback route

Create `app/auth/callback/route.ts` using the official `handleAuth()` helper. The path must exactly match `NEXT_PUBLIC_WORKOS_REDIRECT_URI` and the redirect URI configured in the WorkOS Dashboard.

### 3. Sign-in route/action

Use the official AuthKit authorization/sign-in helper. Do not accept an arbitrary user-controlled return URL without validation.

### 4. Root provider

Wrap the app in the official `AuthKitProvider`. When sending initial auth data to a client provider, remove the access token first; the access token belongs on the server path.

### 5. Server workspace

Use `withAuth()` in the protected server page to obtain the authenticated user and server access token. Pass the token only to server-side helpers such as:

- `listOrganizations()`
- `listRuntimeOptions()`
- `listProjectStatuses()`
- `getExecutiveOverview()`

`app/production-executive-workspace.tsx` already composes those live contracts and refuses a requested organisation that is not present in the current Brain membership list. Executive data is rendered only for the roles expected to hold Brain's organisation-wide audit permission; FastAPI remains the authoritative permission check.

### 6. Ask Brain BFF

Expose a same-origin Next.js route for the browser's Ask Brain form. The route must:

1. call official `withAuth()` server-side;
2. reject an unauthenticated request;
3. obtain the WorkOS access token on the server;
4. validate the organisation identifier as a server-controlled route value/current membership, not as a permission grant;
5. call `askBrain()` from `app/brain-api.ts`;
6. return only the Brain response/error contract;
7. never serialize the WorkOS access token, refresh token, encrypted AuthKit session header, WorkOS API key or Brain provider secrets.

`app/ask-brain-panel.tsx` already calls only a same-origin BFF endpoint and never accepts a bearer token prop.

## Authentication UAT

Use at least these accounts/conditions:

1. unauthenticated browser;
2. Owner/Admin/Executive in Org A;
3. Member/Manager in Org A without `audit.read`;
4. user in Org B only;
5. user who can access Org A but not one restricted Work Graph project;
6. access-revoked user/session case where practical.

Pass only if:

- unauthenticated protected routes redirect/challenge through AuthKit rather than loading live company data;
- the callback establishes a valid encrypted session and does not expose tokens in the URL after completion;
- FastAPI accepts the real AuthKit token with matching `client_id`, issuer, expiry and `urn:brain:user_email`;
- wrong-client, wrong-issuer, expired, malformed and missing-email-claim tokens fail closed;
- Org B cannot select or query Org A;
- frontend role presentation does not override FastAPI permission checks;
- restricted projects/evidence remain absent for a user without the underlying resource permission;
- access revocation is reflected on the next authorised backend read according to the relevant UAT contract;
- no WorkOS access/refresh token, API key, session internals, AWS key, OpenAI key or secret reference appears in HTML, client JavaScript configuration, browser storage, URLs or user-visible error text.
