# Brain Native Conversation Architecture

Story: `S-10.06.01`  
Status: `IN_REVIEW`

## Problem and success boundary

Brain's existing native channel was a flat message list. A daily team surface needs focused channel navigation, root-level threads, exact mentions, reactions and personal unread state while preserving the existing tenant, restricted-channel and evidence boundaries.

Success means zero cross-tenant/revoked disclosure in automated and manual checks; exact root/thread ownership; one allowed reaction per user/value; a read cursor that cannot move backwards; and an authenticated responsive UI whose browser code never receives a reusable Brain bearer token.

AI is deliberately not used. These are deterministic state and permission rules. Rules plus database constraints are cheaper, faster and more accurate than an LLM, RAG, fine-tuning or an agent. There is no training/evaluation dataset because no predictive model exists in this slice.

## Architecture and data flow

1. The authenticated server loads visible channels, personal unread summaries and the selected channel's root messages from FastAPI.
2. Browser mutations go only to a same-origin Next.js BFF route. The route rejects cross-site requests, bounds/parses JSON, loads the WorkOS server session and verifies current Brain organisation membership/role.
3. FastAPI rechecks current organisation permission and current channel read/write access. Browser role claims are never accepted.
4. New messages atomically increment `native_channels.last_message_sequence`. `native_messages.message_sequence` is the stable channel order used by unread state.
5. Root/reply messages reuse the existing RawEvent -> CanonicalEvent -> Work Graph -> Search evidence projection. A reply adds only `thread_root_id`; it does not create a second message store.
6. Exact `@email` tokens resolve only to active organisation members who can currently read the channel. The UI highlights only mentions returned by the server.
7. Reactions and read state are stored under composite tenant/channel/message foreign keys. Revoked restricted-channel access fails before content is returned or changed.

## Persistence

| Table/change | Purpose | Integrity rule |
|---|---|---|
| `native_channels.last_message_sequence` | Atomic channel counter | incremented by one database `UPDATE ... RETURNING` |
| `native_messages.thread_root_id` | Root-only reply relationship | composite self-FK binds organisation + channel + root |
| `native_messages.message_sequence` | Stable channel ordering | unique per channel and non-null |
| `native_message_mentions` | Resolved exact mentions | one row per message/user; composite message scope |
| `native_message_reactions` | Personal reactions | one row per message/user/reaction; five-value DB allow-list |
| `native_channel_read_states` | Personal read cursor | one row per channel/user; numeric cursor only advances |

Migration `20260912_0020` gives existing messages a deterministic `row_number()` within each channel, seeds the channel counter, then makes sequence and scoped constraints mandatory.

## API contract

| Method/path under `/api/v1/organizations/{org}/native-conversation` | Result |
|---|---|
| `GET /channels` | Visible channel unread count, last-read time and latest-message cursor |
| `GET /channels/{channel}/messages` | Root messages with reply counts, mentions and reaction aggregates |
| `POST /channels/{channel}/messages` | Idempotent root message |
| `GET /channels/{channel}/messages/{root}/replies` | Replies for one valid root |
| `POST /channels/{channel}/messages/{root}/replies` | Idempotent root reply |
| `PUT/DELETE /channels/{channel}/messages/{message}/reaction` | Add/remove one allowed personal reaction |
| `POST /channels/{channel}/read` | Monotonically mark through one visible message |

The corresponding BFF paths are same-origin `/api/brain/organizations/{org}/native-channels/...` routes generated by `scripts/activate-workos-authkit.sh`.

## UI contract

The selected channel renders before company cards. The left navigation shows personal unread badges. Each root shows server-resolved mention highlighting, agent attribution, five accessible reaction toggles and a thread action. The thread pane keeps the root in context, loads replies on demand, moves focus to its heading and closes with its button or Escape. At narrower widths, the pane stacks below the channel instead of forcing horizontal overflow.

The component covers loading, empty, read-only, session/permission/not-found/conflict/rate-limit and safe generic error states. Every mutation uses `credentials: "same-origin"`; there is no bearer token, localStorage or sessionStorage path.

## Security and failure controls

- Organisation membership and role are derived server-side from the WorkOS-backed Brain session.
- Current restricted-channel membership is checked for reads and writes. Revocation affects roots, replies, mentions, reactions and unread immediately.
- UUIDs, exact JSON keys, lengths, email, idempotency keys and allowed reactions are validated at BFF and FastAPI boundaries.
- Composite database foreign keys prevent cross-tenant/channel relationship rows even if service code regresses.
- Semantic creation audit keys omit retry-specific request IDs, so a valid idempotent retry cannot conflict with its original audit event.
- Reserved structured-log fields are filtered so telemetry cannot crash message projection.
- Generic HTTP metrics/traces cover these routes without adding tenant/content labels. Message content is not placed in metrics.

## Performance, cost and monitoring

Unread summaries use bounded batched queries instead of one count query per channel. Thread replies load only when opened and API limits are capped at 200 roots/200 replies. The slice adds no model or external-provider cost.

No production latency result is claimed. The inherited S-09.04 core API target is p95 below 500 ms and must be measured with representative channel/message volume before production acceptance. Monitor route error/latency metrics, projection failures, conflict rates and database constraint errors. A new realtime layer is not justified until measured refresh delay or load proves the server-refresh baseline inadequate.

## Rollback

1. Stop deployments/workers that create native messages and block channel writes.
2. Export mention, reaction, thread and read-state rows if that user state must survive rollback.
3. Run `alembic downgrade 20260912_0019`.
4. Deploy the previous application version, which does not read conversation columns/tables.
5. Verify root messages, canonical evidence, Work Graph nodes and Search documents remain available.

Downgrade intentionally deletes thread relationships, mentions, reactions and read cursors. It does not delete the existing root message bodies or their evidence projection.

## Known limitations

There is no WebSocket/live presence, typing state, DM, voice/video, composer attachment, message edit/delete, external notification or fuzzy `@name` lookup in this increment. Server refresh means another user's new message appears on the next navigation/refresh. These limits are explicit; they are not presented as full Slack/Discord replacement behaviour.
